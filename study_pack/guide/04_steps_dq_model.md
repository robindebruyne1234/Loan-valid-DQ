## The rule set {#rules-set}

- **124 rules executed**: 89 written by hand in `dq/dq_rules.yaml` plus 35 generated by a
  per-column completeness sweep.
- Hand-written rules by dimension: validity 26, completeness 23, uniqueness 13, referential
  integrity 12, cross-table consistency 12, reconciliation 3. By severity: block 50, warn 23,
  info 16.
- Every rule carries a **dimension, a severity, a severity rationale written in terms of the
  questions it affects, a handling, and the questions affected**. The loader refuses a rule
  without them — a rule without reasoning "scores the same as no rule" in the brief's words.
- On the public copy **19 rules fire** (block 1, warn 6, info 12), and they describe **14
  defect types** (block 1, warn 4, info 9) — several rules can describe one type, which is why
  the register has fewer rows than the report.

## What each severity does {#severities}

| Severity | Consequence | Delivered run |
|---|---|---|
| <span class="sev block">block</span> | Row quarantined with a reason naming the rule; excluded from core and from the ai views; reversible and countable | 1 rule, **1 row**: `UNQ_TRANS_BUSINESS_KEY` |
| <span class="sev warn">warn</span> | Row kept; flag written to `dq.flags`; flag travels onto the core row (`_dq_flags`) and a caveat with a row count goes into the semantic layer, so it reaches the answer | 6 rules, **440 flags on 352 distinct rows** |
| <span class="sev info">info</span> | Standardised or logged; no answer changes | 12 rules |

:::say The best severity example
"Fourteen postings have amount zero. 'Amount must be positive' sounds obviously right, but
those are real interest postings that accrued nothing. At block I would have quarantined
valid rows and broken fourteen balance chains to fix nothing, so it is info. A *negative*
amount would be block, because it means the sign was applied twice and money moves the
wrong way. Same kind of check, opposite decision, and I can say why for each."
:::

## Proving the rules fire: the defect injector {#injector}

A rule that never fires on clean data proves nothing. `sql/70_inject_defects.sql` builds a
corrupted copy of staging in schema `inject` with **20 seeded defects, one per rule family**,
deterministically. `tests/test_dq.py` asserts each one is caught by the rule meant to catch
it. The ten answers are never computed on that copy (D004).

The injector produced the most useful bug of the project (D008): `dq.v_blocked` was not
scoped by schema, so running the rule tests made the *injected* defects exclude *real* rows —
76 districts instead of 77, 11,024 transactions orphaned. The model checks failed before
any deliverable was written. Fix: the views filter `target_schema = 'stg'`, and a comment
says why the filter is load-bearing. The lesson: verify the model, do not trust a green
build.

## Why a star with a bridge {#why-star}

**Options:** one wide table at posting grain; Data Vault; the source model as-is. **Choice:**
four dimensions from the source tables (client, account, district, card) plus a generated
calendar, a bridge, two base facts and a derived fact. (The documents say "four dimensions";
someone counting `dim_` tables will find five — the fifth is the generated `dim_date`.) **Why:** the ten questions
live at four grains (client, account, loan, posting). A wide table turns every count into
`count(distinct …)` — exactly the construct generated SQL gets wrong quietly. Data Vault
suits many sources with history; there is one source and one extract. **Cost:** joins, each
declared in the semantic layer with a measured cardinality, and a derived fact to rebuild.
Natural keys, not surrogates (D007): one source, no history, and shorter SQL for the model.

## One definition, decided here {#definitions}

| Term | Decided in | Definition |
|---|---|---|
| Account owner | `core.v_account_owner` | The client on the account's `OWNER` disposition; exactly one per account (block rule `UNQ_ACCOUNT_SINGLE_OWNER`, 4,500 owners for 4,500 accounts) |
| Problematic loan | `fact_loan.is_problematic` | Status B (finished, unpaid) or D (running, in debt): 76 of 682 (A4) |
| Incoming money | `fact_transaction.direction = 'credit'` | Type `PRIJEM`, summed on the unsigned amount (A7) |
| Month-end balance | `fact_account_month_end_balance` | Balance after the last posting on or before the month end; carried forward when the month had none (A14, A15, D019) |
| Owner's age at loan start | `v_loan_enriched` | Exact fractional years from the decoded birth date (A10) |

## The month-end balance, and its known limitation {#month-end}

D019 builds one row per account per month end from the account's first posting month to
1998-12: the balance after the latest posting in that month; a month with no posting carries
the previous balance forward, with `is_carried_forward` and `balance_as_of_month_end`
exposed (558 such rows). Options rejected: compute it on the fly per query (two answers to
one question guaranteed), or skip quiet months (biases the average upward).

**The limitation.** When an account has several postings on its last day, the delivered
rule picks the one with the **highest `trans_id`** — but the source records no time of day
and `trans_id` is not chronological. Interest postings carry high ids but are booked before
the month's statement fee, so the rule often reads the balance *before* the fee. This was
disclosed at delivery (A14, caveat C2, DDR §3, delivery audit item 3) as a known limitation:
Q9's average barely moves; individual balances do.

:::post What changed after delivery (D028)
The running balance *does* record the order: each posting starts at `balance_after −
signed_amount`, so the postings of a day form a chain and its end is the closing posting.
Over 185,057 posted account-months the chain resolves 98.8%; the highest id picked the right
posting only 0.4% of the time. Q9 moves from 43,808.94 to 43,810.47; 107 accounts close
differently at 1998-12-31, by up to 1,200.00 CZK. Lessons Learned L-01 has the full story.
:::

## Verified after every build {#verified}

`build_model` checks primary keys, foreign keys, declared grains (one row per key), code
labels against `ref_codes`, and `core = stg − quarantine`; the delivery run reported 0 key,
foreign key, grain or code problems and 9 balanced reconciliation checks. Rebuilding core
drops the `ai` views that depend on it, so `make model` restores the views, policies and
grants in the same command (D012) — a lesson learned when a single re-run left the AI surface
missing.
